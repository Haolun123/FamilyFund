# Father Fund：独立交易与仓位跟踪

第一版实现日期：2026-11-04。入口为 Dashboard 的 Father Fund 标签页。

**状态说明**：第二版快照流程已实现（2026-11-04）。前半部第一版说明作为历史设计保留；当前操作按下方“第二版设计与实现”及`USER_MANUAL.md`执行。实现仅涉及Father Fund，不同步Obsidian。

## 用户目标与第一版范围

父亲证券账户独立核算，用20%—30%的权益区间跟踪退出及重新配置进度。功能包括期初及历史成交导入、立即保存成交、资金变动、行情/手工估值、调整计划、完整流水导出、撤销/纠错、券商快照对账。暂不提供自动交易、日内风控、自动清仓或完整TWR/最大回撤曲线。

父亲资金、交易和损益不计入原FamilyFund或Son Fund。第一版不自动生成合并风险报表，避免将独立资产重复计入。

## 文件及计算

- 页面：`dashboard/father_tab.py`，由主应用挂到Father Fund。
- 引擎：`src/father_fund.py`；不复用主账户的Cash/Company_Stock外部现金流选择规则。
- 独立数据：默认主数据目录下`father/ledger.csv`，可用`FAMILYFUND_FATHER_DATA`覆盖。
- 输入表：优先`FAMILYFUND_FATHER_INPUT`，其次Obsidian的`familyfund/_father_input.md`，最后数据目录`father/_father_input.md`；缺失时显示随页面打包的空模板。
- 环境中的Obsidian路径由`OBSIDIAN_VAULT_PATH`指定，现有Docker挂载可直接使用。

单个CSV流水为唯一事实源，列为事件编号、记录时间、发生时间、类型、JSON内容。没有“流水保存但持仓表尚未保存”的双文件提交问题。日期统一使用北京时间的无时区ISO时间。按发生时间重放，记录时间保留审计顺序。

事件：OPEN期初、TRADE成交、CASH资金、QUOTE估值、PLAN计划、BROKER券商快照、VOID撤销。修正交易使用同一批次追加VOID与替代TRADE，原记录不删除。撤销引起后续超卖或现金不足时拒绝整个改动，用户应改为能自洽的纠正记录。

每次写入持有独立账户锁，锁内读取现有流水、验证重放、追加并经`nav_engine._atomic_write_csv()`原子写入，再检查行数和内容。继承滚动备份，另在每次覆盖前保留临时原文备份。不会调用主账户transaction.csv写入逻辑。

## 金额语义

- 买入按实际人民币扣款减少现金；卖出按实际人民币净到账增加现金。输入为正数，方向决定正负。
- 费用字段已含在实际收付中，仅用于核对，不能重复扣费。
- 港股成交原价和币种独立保存，市值使用价格×股数×报价汇率；现金使用实际人民币结算，不用后来汇率回算。
- 现金入金/出金才计入外部净流量；股息、利息属于收益，费用属于损失。分红再投资记现金分红与买入两笔。
- 接手以来损益＝当前总资产－期初总资产－外部净入金。使用已保存价格，无日内实时收益保证；不冒充TWR或原券商全历史盈亏。
- 期初价格是基准估值，历史负成本不参与期初资产计算。

## 防错与对账

成交必须有唯一券商编号或自编编号，同一提交事件编号重试幂等。多笔真实相同成交可使用各自编号。禁止负数量、非有限数、无效币种、重复期初、期初前交易、超卖与历史时点负现金。

计划只改变状态。估值只改变价格汇率，保留逐项报价时间；过旧报价不覆盖后来的成交或估值。场内资产使用市场报价路径；场外公募使用基金净值路径，不根据“权益”类别猜测交易场所。行情逐项串行请求，失败项目不覆盖旧值。日级行情的时间标记为该日收盘端点，当日则用获取时刻，界面不声称是精确成交时间。

券商总资产、市值、可用分别保留。可用不自动当作净现金，“市值＋可用－总资产”作为口径差异显示，绝不生成调平收入。对账按券商快照时间重放，后续成交不会与旧快照直接误比；持仓完整清单用于数量核对。报价尚未对齐时，金额差异需要人工解释。

最新用户持仓只预填到Markdown的对账区域；期初日期和净现金未齐前不会创建真实流水。推断的腾讯汇率不作为确认行情写入。

## 第二版设计与实现（2026-11-04）

### 1. 范围与保存流程

仅在Father Fund这个Tab内完成录入、标的确认、行情刷新、持仓核对、保存和业绩展示。主基金和Son Fund的当前设计、界面、记账流程及数据不变；不建设三账户共用的新账本，也不迁移另外两个账户。

Father Fund采用现有主基金、Son Fund的快照工作方式：

1. 在text box粘贴本期交易CSV。
2. 逐行解析、匹配标的，补充并确认新标的信息。
3. 预览交易清单、份额及现金变化，应用到待保存持仓。
4. 主动刷新一次价格/净值；失败项手动填写并确认。
5. 根据确认后的持仓、价格及汇率重算市值。
6. 核对后统一保存快照，交易及持仓才正式落盘，更新净值和盈亏。

页面必须明确显示待保存状态，避免用户把解析或应用误认为已入账；同一批记录不能重复应用。快照保存使用已应用交易的结果，不再执行一次买卖。

### 2. 交易CSV格式

text box接受每行一笔交易的六列CSV，字段顺序为：

```text
日期,买入/卖出,代码,股数或份额,原币成交价,人民币收付金额
```

以下为本轮已确认交易的格式示例：

```text
2026-11-02,卖出,513330,150000,0.314,47100
2026-11-02,买入,00700.HK,100,389.2,33113.20
```

分别对应华夏恒生互联网科技业ETF（513330）和腾讯控股（00700.HK）。日期为交易日期，快照日期单独选择；币种、名称和类型从标的资料匹配。数量及人民币收付填正数，方向决定现金增减：买入填实际含费扣款，卖出填净到账，不要求另列手续费。不能用后来行情汇率覆盖历史人民币结算金额。

本轮历史输入按用户授权采用简化口径：2026-11-02为期初基准，期初现金11000元，腾讯控股（00700.HK）买入100股；这几天费用忽略。腾讯33113.20元为保留389.2港元成交价、使用同花顺数据反推汇率后的估算收付，不标作已核实结算。估算注记应保留。该历史简化不自动推广为后续所有成交均忽略费用。

### 3. 标的识别与首次建仓

识别顺序：父亲账户自己的已确认标的映射及持仓 → 主基金当前持仓及对应映射 → 手动补充。主基金只作为只读参考；不将主基金的数量、成本、现金或持仓决策复制到父亲账户。

匹配前规范化代码别名，例如腾讯控股的HK0700、00700.HK、0700.HK应识别为同一标的。别名用于匹配，账户代码和行情代码仍分别保存。

两边均无法匹配时，在该CSV行旁显示手动填写区：名称、代码、股票/场内ETF/场外基金类型，并确认币种。系统依据代码和类型生成候选行情来源、行情代码，允许用户核对。点击确认时查询一次标的信息及价格，显示结果供用户确认是否为目标标的。

| 验证结果 | 处理 |
|---|---|
| 标的身份、行情映射及价格均有效 | 可确认新标的并用于本期交易 |
| 标的身份及映射已验证，价格暂时获取失败 | 手动填写价格后可确认 |
| 标的身份或代码有效性无法验证 | 保留待验证草稿，不作为已确认新标的入账 |

仅符合代码格式不等于已验证API映射；不得因网络失败而把任意手填代码标成已验证。名称查询成功也不能替代股票/ETF/场外基金类型和币种确认。

### 4. Father Fund独立持久化

运行数据继续位于iCloud同步的`$FAMILYFUND_DATA`内，父亲账户数据全部放在独立的`father/`子目录，不进入主基金的配置文件。新标的资料持久化为：

```text
$FAMILYFUND_DATA/
├── portfolio.csv                   原主基金文件，保持原样
├── son/                            原Son Fund目录，保持原样
└── father/
    ├── ledger.csv                  第一版既有流水，需保留
    ├── instrument_map.json         父亲账户自己的标的映射
    └── backups/                    父亲账户流水及映射的滚动备份
```

`instrument_map.json`的资料包含账户代码、名称、别名、资产类型、币种、行情来源、行情代码及验证状态。已确认资料用于后续CSV识别及行情刷新；待验证资料仍为草稿，不参与正式交易或估值。

从主基金匹配来的标的信息，经用户确认后保存一份到父亲账户自己的映射中。以后独立使用，不随主基金映射修改而自动变化。重启Dashboard或换设备后仍可识别已确认标的。复用现有函数时也不得触发主基金配置的迁移或写入副作用。

价格、净值、汇率和行情日期属于父亲账户估值/快照；实际人民币收付属于交易记录，均不以标的映射文件作为历史金额来源。标的信息确认持久化不等于交易已保存，两者在页面上区分。

写入需保留原文件备份并采用原子写入；CSV沿用项目规定的`nav_engine._atomic_write_csv()`。既有Father Fund流水及历次输入不得因新流程被静默删除、重算或重复导入。

### 5. 行情映射及获取失败处理

2026-11-14：手动报价新增独立“手动报价实际日期”字段，周末补录默认前周五，用户确认后将该日期记入报价as_of，快照effective_at仍保留实际记录日期；表格手改和失败后手动确认共用此日期。周末价格是否过期以该周周五为期望日，而非周末录入日。原流水不改写。

复用现有`price_fetcher.fetch_latest_prices()`等拉取能力；沿用Ledger页“主动拉取一次，失败后手动填写”的交互。多数据源是按资产类型路由，不承诺每个标的都有多API自动兜底，也不新增自动循环或逐项重试流程。

| 标的 | 账户代码 | 行情代码或来源 |
|---|---|---|
| 腾讯控股（00700.HK） | 00700.HK | yfinance 0700.HK，另获取HKD/CNY汇率 |
| 友阿股份（002277） | 002277 | yfinance 002277.SZ |
| 华夏中证机器人ETF（562500） | 562500 | yfinance 562500.SS，取场内价格 |
| 场外公募基金 | 对应六位基金代码 | 天天基金公布净值，不强制配置yfinance |

现有`yf_symbols.json`主要服务基本面映射，不能假定每条基本面查询代码都对应持仓市值所需的报价市场。Father Fund持久化自己的行情映射；场内ETF使用交易价格，场外基金使用公布净值。

刷新针对本期待保存持仓，包含本期新建仓标的。成功项更新待保存价格，外币资产同步更新成功获取的报价汇率；显示行情日期、成功/失败/需手动数量及详情。失败项旁提供价格/净值输入框及确认按钮，外币汇率也可手动补充。未补齐项目保留原值并明确提示，不能用0或无效值覆盖旧价格。

按确认后的数据计算：

- 持仓人民币市值 = 股数或份额 × 原币价格 × 人民币/原币折算汇率。
- 账户总资产 = 所有持仓人民币市值之和 + 账户现金。

价格刷新、手动确认和重算均作用于待保存快照；最终保存后才更新正式业绩记录。正常情况下用户无需逐行手改市值，手动填写用于自动获取失败时的补充。

### 6. 接手以来的展示口径

已确认的核心展示包括总资产、现金、接手以来累计盈亏、当前持仓盈亏、单位净值及净值曲线；保留Father Fund现有权益仓位目标展示。

- 接手以来累计盈亏 = 当前总资产 − 期初总资产 − 接手后的外部净入金。
- 单位净值采用现有基金的份额净值口径，剔除外部入金/出金影响，随已保存快照更新。
- 当前持仓盈亏从接手时估值作为期初成本开始，结合接手后买卖计算，不追溯接手前的历史亏损。

交易解析未保存、行情未更新或没有保存新快照时，不声称正式净值和盈亏已更新为实时数据。当前已确认范围不新增券商实时盈亏同步、自动交易、三账户合并核算或新的成本算法。

### 7. 实现决策与验证

- 沿用唯一金融事实源`father/ledger.csv`，新增完整估值`SNAPSHOT`事件。已应用的交易、资金、纠错和估值在同一批次原子追加；不新增第二份交易/持仓CSV，不迁移既有数据。账户锁内检查草稿基准版本，其他页面更新后拒绝过期草稿；同请求同内容重试幂等。
- 每日一个有效快照。重做同日快照需先追加撤销记录，原快照仍保留。无证券持仓也可保存现金快照。
- CSV相同行完整保留，每行生成独立批次编号。同一批次应用后禁用再次应用；新批次与已有/待保存交易内容相同时提示并要求确认。重新解析可录入另外发生的真实相同成交，不静默去重。
- 账户代码规范化用于匹配，现有Father持仓代码保留。新标的API返回代码、类型及币种都必须匹配；无法验证仅保存pending资料。股票/ETF的行情代码须与账户代码对应，不能把其他股票的有效报价误绑定到当前标的。查询异常只保存通用失败信息。
- 金额不从映射中恢复。注册资料的保存与金融快照分开；映射原子合并、锁定写入，保留临时原文备份和最多30份滚动备份。
- 内存快照从期初和已保存SNAPSHOT派生；旧QUOTE估值检查点保留。无新快照时可显示既有历史成交的最终状态；新批次交易本身不增加临时净值点。Cash NCF只记外部资金，资产NCF按买卖人民币收付累计，复用现有`compute_fund_nav()`、`compute_cost_basis()`。不引入FIFO、移动平均成本、额外已实现盈亏或XIRR指标。
- 刷新与手动修改作用于会话草稿。失败不覆盖成功值；旧报价或成交估算需显式接受后方可保存，非法/非有限价格和汇率不能用于入账。未保存记录及应用后的现金、持仓都可预览。
